Une machine à états, c'est une représentation formelle du cycle de vie d'un objet : un ensemble fini d'états possibles, et un ensemble de transitions autorisées entre ces états. Tout ce qui n'est pas explicitement autorisé est interdit.

L'item passe par 6 états : en stock, alloué, en transit, déployé, en maintenance, perdu. 
Les transitions sont strictement contrôlées par une table ALLOWED_TRANSITIONS dans l'entité. Toute tentative de transition non autorisée renvoie un 422 avec la liste des transitions valides. C'est l'encapsulation POO appliquée à une machine à états : impossible de corrompre l'état depuis l'extérieur.

Verrouillage optimiste, le filet pour la sync offline
Pessimiste, non retenu
Verrouiller avant d'écrire.
On pose un lock, on modifie, on libère. Sûr pour la cohérence mais bloquant, impossible à demander à des agents terrain qui scannent hors-ligne.
Optimiste, mon choix
Lire, modifier, vérifier la version au commit.
Compare-and-swap atomique sur __v. Pas de blocage. Les conflits sont détectés au moment de l'écriture, exactement ce qu'il faut pour le offline.
Scénario terrain : pourquoi c'est critique
09h00
Agent A scanne hors-ligne dans un sous-sol.
09h05
Agent B scanne le même item en ligne. __v passe à 2.
09h12
Agent A retrouve le réseau et POST avec __v: 1.
→ 409
Le serveur détecte le conflit. La PWA re-GET, merge côté client, re-soumet.
▸
Mongoose maintient __v automatiquement à chaque save
▸
Chaque update matche sur { _id, __v }, opération atomique
▸
Si findOneAndUpdate retourne null → ConflictError 409
▸
La PWA reçoit 409 et déclenche un merge côté client

Le verrouillage optimiste, c'est un pattern qui fait la promesse opposée du verrouillage pessimiste classique.En pessimiste, on pose un verrou avant de modifier, risque de blocage si quelqu'un oublie de libérer. En optimiste, on ne verrouille rien : on lit, on travaille, et au moment d'écrire on vérifie que la version qu'on avait n'a pas changé entre temps. Techniquement c'est un compare-and-swap atomique.Mongoose maintient un champ __v qui s'incrémente automatiquement à chaque save. 
__v est un champ automatique de Mongoose qui sert à tracker les modifications d'un document. 
Mon update repository matche sur { _id, __v: versionAttendue }. Si quelqu'un d'autre a modifié le document entre temps, le __v a changé, et findOneAndUpdate retourne null. Je lève alors ConflictError, code 409.POURQUOI C'EST CRITIQUE POUR LOGICHAINLa PWA va tourner hors-ligne. Un agent terrain scanne un item à 9h dans un sous-sol sans réseau, un autre scanne le même item à 9h05 dehors avec du réseau.Quand le premier retrouve du réseau et synchronise, il faut détecter le conflit pour pouvoir merger. Le 409 est l'API contractuelle pour ça, la PWA reçoit 409, refait un GET, merge intelligemment côté client, et re soumet avec la nouvelle version.Pessimiste aurait été impossible : on n'allait pas demander aux agents terrain de poser un verrou avant chaque scan.

Transactions ACID et allocation atomique d'un lot
Réserver d'un coup tout le matériel d'un secteur, sans jamais laisser un état incohérent
LE PROBLÈME
Au montage, on réserve d'un coup tout le matériel d'un secteur (50 items). Si l'item n°37 est déjà perdu, que deviennent les 36 déjà traités ?  Sans transaction → état incohérent, ingérable en offline.
LA SOLUTION
repo.withTransaction() ouvre une session sur le replica set rs0. Tout-ou-rien : un seul échec (404 / 422 / 409) annule l'intégralité du lot. Le verrouillage optimiste __v reste actif → isolation.

Le verrouillage optimiste qu'on vient de voir protège UN document. Mais au montage, un responsable logistique réserve d'un coup tout le matériel d'un secteur : parfois 50 items en une action. La question, c'est : que se passe-t-il si le 37e item est déjà perdu ou déjà alloué ailleurs ?

Sans transaction, on se retrouve avec 36 items alloués et 14 non traités : un état incohérent, impossible à rattraper proprement, surtout en mode offline où le client ne peut pas deviner ce qui a réellement été écrit.

Ma réponse, c'est une transaction ACID. La méthode withTransaction du repository ouvre une session sur le replica set rs0. C'est du tout-ou-rien : si un seul item échoue : 404 introuvable, 422 état non allouable, ou 409 conflit de version : toute la transaction est annulée. Aucun item n'est alloué, on revient à l'état initial.


Et point important : le verrouillage optimiste sur __v reste actif À L'INTÉRIEUR de la transaction, ce qui me donne l'isolation entre deux opérateurs simultanés.

Sur les quatre lettres d'ACID : l'Atomicité c'est le rollback automatique ; la Cohérence, c'est que chaque item est validé par sa machine à états avant d'être écrit ; l'Isolation vient du __v et du snapshot de transaction ; la Durabilité, c'est le commit répliqué sur rs0.

J'ai prouvé ce comportement en conditions réelles : un lot avec un item invalide laisse bien tous les autres en stock, et un lot valide les alloue tous.

[Si question "pourquoi pas une transaction par item ?"] Parce que ça ne donnerait
PAS l'atomicité du lot : on retomberait dans le cas 36 réussis / 14 échoués. C'est
justement le périmètre métier , « ce secteur, en un geste » , qui doit être atomique.

[Si question "c'est quoi rs0 / un replica set ?"] Un groupe de serveurs Mongo qui
gardent la même copie des données : un PRIMARY qui reçoit les écritures, des
SECONDARY qui répliquent. Si le primary tombe, un secondary est élu : c'est la
tolérance aux pannes. Et c'est la condition technique des transactions ACID et des
Change Streams.

REST RICHARDSON NIVEAU 2Le modèle de maturité de Richardson est une grille à 4 niveaux qui mesure à quel point une API est REST.- Niveau 0 : un seul endpoint qui reçoit tout, façon RPC sur HTTP.- Niveau 1 : on découpe par ressources.- Niveau 2 : on utilise les verbes HTTP de manière sémantique et les codes statut standards.- Niveau 3 : HATEOAS, l'API renvoie les liens vers ses ressources.Le sujet impose le niveau 2 minimum. (((((Je suis exactement à ce niveau, HATEOAS aurait été du sur-engineering pour une PWA qui connaît déjà sa structure.)))))Donc : verbes sémantiques. GET pour lire, POST pour créer, PATCH pour modifier partiellement, DELETE pour supprimer. PUT je n'utilise pas car on ne remplace jamais un item entièrement.Et pour les actions métier qui ne sont pas CRUD, scanner, allouer, déployer, je fais POST sur une sous-ressource verbeuse : POST /items/:id/scan, POST /items/:id/allocate. C'est un compromis acceptable au niveau 2.LES CODES STATUT, MA GRILLE DE DIFFÉRENCIATION- 400 si Zod refuse l'input (mal formé)- 422 si la règle métier refuse, par exemple une transition d'état interdite, l'input est syntaxiquement valide mais le métier dit non- 409 si conflit de version optimistic ou clé unique violée
-403 forbiddennTrois codes différents pour trois échecs sémantiquement distincts, c'est ça, Richardson niveau 2 bien fait.

La sécurité n'est pas une couche qu'on rajoute à la fin, elle est pensée à chaque étage de l'API  du token de l'agent jusqu'à l'écriture en base.

L'authentification se fait par JWT Bearer signé en HS256. Le secret fait au moins 32 caractères, et il est validé au démarrage par Zod : si le secret est trop court, l'application refuse de booter. C'est du fail-fast, on ne tourne jamais en config non sécurisée.

Les mots de passe ne sont jamais stockés en clair : Bcrypt avec 12 rounds. Et le champ passwordHash est en select:false dans Mongoose, donc il ne remonte jamais, même par accident, dans une réponse JSON.

L'autorisation, c'est du RBAC à quatre rôles : admin, responsable logistique, agent de terrain, transporteur : appliqué par un middleware requireRole. Un rôle insuffisant renvoie un 403 Forbidden, distinct du 401 qui, lui, veut dire « pas
authentifié ».

La validation se fait en profondeur, sur deux niveaux : Zod valide la requête HTTP en entrée, puis Mongoose re-valide avant l'écriture en base. Les deux sont volontaires : défense en profondeur.

Côté durcissement HTTP : Helmet pour les en-têtes de sécurité, CORS en liste blanche, une limite de corps à 1 Mo contre les abus, et x-powered-by désactivé pour ne pas divulguer la stack.

Enfin le transport : HTTPS avec certificat Let's Encrypt via Traefik, et surtout MongoDB n'est jamais exposé publiquement : il n'écoute qu'en local derrière l'API.

[Si question "et la validation native MongoDB ?"] J'ai fait le choix de la validation
au niveau de l'ODM Mongoose plutôt que des validateurs $jsonSchema natifs : ça me
donne des types TypeScript portables et l'autocomplétion, tout en gardant une
double barrière Zod + Mongoose.

Le troisième objectif, c'est le pilotage : donner aux responsables des indicateurs en temps réel. Plutôt que de charger tous les items et de compter côté Node (ce qui serait lent et coûteux en mémoire) je fais le calcul au plus près de la donnée, dans MongoDB, avec un pipeline d'agrégation.

La clé, c'est l'opérateur $facet : en un seul passage sur la collection, je calcule plusieurs métriques à la fois,  le nombre d'items par statut, par catégorie, le poids total, et le CO2 de fabrication cumulé. Une seule requête au lieu de quatre.

Architecturalement, ce pipeline est isolé dans le Repository. C'est une exigence du sujet : toute la logique d'accès aux données, y compris les agrégations, reste confinée à la couche data. Le service ne voit jamais de requête Mongo.

Cette agrégation alimente trois choses : le tableau de bord d'état des stocks, l'empreinte carbone consolidée d'un événement, et la détection des goulots d'étranglement. Le tout exposé par les endpoints du dashboard.

Le bloc de code en bas, c'est la structure réelle du $facet : un $match pour cibler l'événement, puis trois sous-pipelines parallèles regroupés par statut, par catégorie et pour les sommes.

pas les milliers de documents. C'est ce qui tient la charge sur un gros événement.

L'algorithme du banquier répond à une seule question :

▎ « Si j'accorde cette demande de matériel maintenant, est-ce que je reste capable de servir tous les événements jusqu'au bout, ou est-ce que je risque de me retrouver coincée ? »

Si la réponse est « je reste capable » → on accorde. Sinon → on refuse (HTTP 422). On simule avant d'accorder, on n'attend pas que le blocage arrive.

Analogie de la banque (d'où le nom) : un banquier prête de l'argent à plusieurs clients. Chaque client a annoncé un besoin maximum. Le banquier n'accorde un retrait que s'il lui reste assez pour satisfaire tout le monde. dans notre cas : le « banquier » = le pool d'équipements, les « clients » = les événements.

Ici je montre comment l'API est documentée. Le point important : la doc n'est pas écrite à la main, elle est générée automatiquement à partir du code.

1. Single source of truth : On utilise Zod pour valider les requêtes entrantes. Avec la librairie zod-to-openapi, ces mêmes schémas Zod produisent aussi la spec OpenAPI 3. Résultat : un seul schéma sert à la fois à valider la requête et à documenter l'endpoint. La doc ne peut donc jamais être désynchronisée du code réel : si je change un champ, la doc se met à jour toute seule.

2. UI Scalar : Cette spec OpenAPI est ensuite affichée par Scalar, servi sur la route /docs. OpenAPI, c'est le format standard ; Scalar, c'est juste l'outil qui l'affiche joliment : équivalent à Swagger UI, en plus moderne. On a 35 endpoints documentés, avec le bouton « Try it out » pour tester en direct et un bouton « Authorize » pour coller son token JWT.

3. Protégée par Basic Auth : /docs et /openapi.json sont derrière un login HTTP Basic. Détail sécu : la comparaison des identifiants se fait à temps constant (timingSafeEqual sur des hash SHA-256), pour ne pas laisser fuiter d'info par timing. On évite d'exposer publiquement la structure complète de l'API.

 4. La vitrine de l'API : Comme le projet n'a pas de frontend, cette doc interactive est l'interface de démonstration : je peux montrer l'API en marche, en direct devant le jury, sans écrire une ligne de code client.

DIRE QUE : l'API ne se contente pas du strict énoncé, elle complète les cycles de vie (CRUD complet, retour/perte d'items) et ajoute des briques d'ingénierie (refresh token, health check, cache ADEME auditable, allocation ACID, algorithme du banquier).

Slide temps réel. Le sujet demande des notifications critiques en temps réel. Je l'ai implémenté côté serveur avec deux briques : les Change Streams MongoDB, qui surveillent les écritures en base sans polling, et un canal Server-Sent Events (SSE) qui pousse l'alerte à l'agent connecté. Quand une anomalie est déclarée sur un item, le Change Stream la détecte, le service construit une notification critique, la persiste dans la collection notifications, puis la diffuse aux agents abonnés. Latence mesurée en démo : ~7 ms entre l'action terrain et la réception. La persistance permet à un agent déconnecté de récupérer les alertes manquées via GET /notifications.
