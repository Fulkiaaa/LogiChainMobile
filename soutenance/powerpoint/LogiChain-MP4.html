01 Le problème

Le terrain n'est pas un bureau

L'API garantit la cohérence des données. Elle ne sert à rien si personne ne peut les saisir là où elles naissent : dans la boue, dans un sous-sol, à 6 h du matin, avec une seule main libre.

02 Ce que le sujet demande

Quatre objectifs

Chacun se traduit par une décision d'architecture précise, que je démontre dans la suite.

05 Décision structurante

React Native pur,
pas Expo

Une décision prise au premier jour, jamais remise en cause — et qui a eu un coût réel, que j'assume.

Pourquoi

Le projet a besoin d'accès natifs pointus : caméra en mode scanner continu, trousseau sécurisé, géolocalisation à la demande, SQLite en JSI. En bare workflow, j'écris directement dans le projet Xcode : permissions, pods, signature. Rien n'est masqué par une couche d'abstraction.

Le coût, constaté

La génération actuelle de @react-native-vector-icons déclare @expo/config-plugins en dépendance de pair. Elle est donc inutilisable ici. J'ai basculé sur Lucide + react-native-svg — et ce contretemps s'est révélé être un meilleur choix : les icônes SVG héritent de la couleur, donc elles suivent le thème clair/sombre sans une ligne de code en plus.

Ce que je retiens : une contrainte d'architecture posée tôt ferme des portes plus tard. Le travail n'est pas d'éviter ça, c'est de savoir quelle porte on ferme, et de vérifier qu'il existe une autre issue.

Conduite

C'est ta slide « décision d'ingénieur ». Le jury aime les décisions documentées avec leur coût — pas les choix présentés comme évidents.

Raconte-la comme une petite histoire : contrainte posée → problème rencontré des semaines plus tard → solution qui s'est avérée supérieure. Ça montre que tu traces tes décisions.

Si on demande « Expo aurait marché ? » — oui, probablement, avec un development build. Mais le sujet impose React Native et je voulais garder la main sur le projet natif ; sur un scan caméra en continu, c'est là que se jouent les performances.

└───────────────────────────────┬───────────────────────────────────────┘
                                │ appelle

                                │ appelle
┌─ SERVICES ───────── services/ + domain/ ─▼───────────────────────────┐

│  domain/ = règles métier pures, testables sans device                 │

La règle d'or : un écran importe des hooks/, jamais des services/. La séparation physique des dossiers rend la violation visible en revue de code — c'est la même logique que le N-Tier de l'API : chaque couche ne connaît que celle du dessous.

Conduite

Fais le parallèle explicite avec le MP3 : là-bas c'était Entity / Repository / Service / Controller. Ici c'est UI / Hooks / Services. Même principe, appliqué à un contexte différent — ce n'est pas une recette recopiée, c'est le même raisonnement.

Le dossier domain/ mérite une phrase : j'y ai isolé toutes les règles pures — machine à états, matrice de permissions, décision de réconciliation, filtrage. Aucune dépendance à React ni à React Native. C'est pour ça que je peux avoir 298 tests qui tournent en une seconde sans simulateur.

Si on demande la preuve que la règle tient : grep -r "services/" src/screens — l'écran de scan ne connaît que useScanner.

08 Offline-first

SQLite est la source
de vérité locale

Pas un cache d'appoint : la base embarquée est ce que l'app lit, toujours. Le réseau ne fait que la rafraîchir.

CREATE TABLE items (id TEXT PRIMARY KEY, qrCode TEXT, label TEXT,
  category TEXT, status TEXT, eventId TEXT, lng REAL, lat REAL,
  weightKg REAL, version INTEGER, updatedAt TEXT, syncedAt TEXT);

CREATE INDEX idx_items_qrCode  ON items(qrCode);   -- le scan tape ici
CREATE INDEX idx_items_status  ON items(status);
CREATE INDEX idx_items_eventId ON items(eventId);

events · zones

Le secteur assigné : l'événement actif et ses zones géographiques, téléchargés une fois à la connexion.

items

Les 51 équipements du secteur. Index sur qrCode : c'est lui qui rend le scan instantané.

sync_meta

Clés-valeurs : secteur assigné, dernière synchro complète, mode de thème choisi.

Les migrations sont idempotentes (IF NOT EXISTS) et rejouées à chaque ouverture. Une app terrain ne peut pas se permettre un échec de migration à 6 h du matin sur un parking.

Conduite

Le point à faire passer : l'app ne lit jamais le réseau pour afficher quelque chose. Elle lit SQLite. Le réseau alimente SQLite, en arrière-plan. C'est ce renversement qui rend le mode hors ligne transparent — il n'y a pas de « mode dégradé », c'est le même chemin de code.

L'index sur qrCode est le point sensible : c'est lui qui fait tenir la promesse du scan en rafale. Sans index, un balayage complet à chaque code lu.

Si on demande pourquoi SQLite et pas AsyncStorage : AsyncStorage est un magasin clé-valeur, il ne sait ni indexer, ni filtrer, ni trier. Le sujet demande explicitement des requêtes relationnelles sur des milliers d'enregistrements.

09 Offline-first

Ce qu'on garde,
ce qu'on jette

La stratégie de cache n'est pas éparpillée dans le code : elle est déclarée à un seul endroit, data/cacheManifest.ts.

itempersisté, jamais purgé — mis à jour en upsert à chaque synchro12 champs

Décision assumée : je ne cache que ce dont l'UI a besoin hors ligne. L'historique d'un équipement peut peser lourd et ne sert qu'à la consultation ponctuelle d'une fiche — le mettre en cache aurait fait grossir la base pour rien.

Conduite

Ce qui compte ici, ce n'est pas la liste : c'est le fait qu'elle soit déclarative et centralisée. Quand la stratégie de cache est répartie dans dix fichiers, personne ne sait plus ce qui survit à une déconnexion. Là, il y a un fichier à lire.

La ligne rouge est ton exemple d'arbitrage : j'ai choisi de ne pas tout cacher, et je peux dire pourquoi.

10 Le cœur du projet

La file sortante

Tout ce que l'agent fait devient une ligne dans une table. C'est la pièce centrale de l'application : sans elle, il n'y a pas de mode hors ligne.

CREATE TABLE outbox (
  localId     TEXT PRIMARY KEY,   -- uuid généré sur le téléphone
  createdAt   TEXT NOT NULL,     -- l'ordre de rejeu, FIFO
  entityId    TEXT NOT NULL,     -- l'équipement concerné
  actionType  TEXT NOT NULL,     -- scan | transit | deploy | anomaly | lost…
  payload     TEXT NOT NULL,     -- JSON : position GPS, note…
  baseVersion INTEGER,           -- ⚠ la version de l'item AU MOMENT du geste
  status      TEXT NOT NULL,     -- pending | failed | conflict
  attempts    INTEGER DEFAULT 0,
  lastError   TEXT);
baseVersion est le lien direct avec le MP3. C'est le __v du verrouillage optimiste que j'ai présenté côté API. L'app le capture au moment du geste et le renvoie à la synchro : c'est ce qui permet au serveur de détecter qu'un autre agent est passé entre-temps et de répondre 409.

Conduite

C'est la slide du projet. Prends ton temps.

Fais le lien explicitement : « en MP3, j'ai présenté le verrouillage optimiste et le code 409, en disant que la partie mobile en aurait besoin. Voilà où il atterrit : dans une colonne d'une table SQLite sur le téléphone. »

Le scénario du MP3 se rejoue ici pour de vrai : l'agent A scanne à 9 h dans un sous-sol — baseVersion: 1 écrit en local. L'agent B scanne le même équipement à 9 h 05 — le serveur passe à la version 2. À 9 h 12, A retrouve le réseau, envoie sa ligne avec baseVersion: 1 → 409.

Si on demande pourquoi un localId en uuid : la ligne existe avant que le serveur n'en sache quoi que ce soit. Il lui faut une identité côté client, sinon on ne peut ni la retrouver, ni la dédoublonner, ni la supprimer après confirmation.

11 Optimistic UI

Le geste, puis
la promesse

1L'agent appuie« Déployé » sur une fiche équipement, ou un QR entre dans le champ de la caméra.
2Une transaction SQLite, deux écrituresLe statut local passe à deployed et une ligne est empilée dans la file sortante. Les deux ensemble, ou aucune des deux.
3L'écran est déjà à jourVibration, bip, compteur incrémenté. L'agent enchaîne. Aucun appel réseau n'a eu lieu.
4Plus tard, le réseau revientLe moteur de synchro vide la file dans l'ordre. Ça peut être dans dix secondes ou dans deux heures : l'agent, lui, a fini son geste.
L'optimistic UI n'est pas un effet cosmétique : c'est un engagement. L'app affirme un résultat que le serveur n'a pas encore validé. Elle doit donc savoir revenir en arrière — c'est l'objet des deux slides suivantes.

Conduite

Insiste sur l'étape 2 : la transaction. Si le statut local changeait sans que la ligne de file soit écrite, l'agent verrait « déployé » à l'écran et le serveur ne l'apprendrait jamais. C'est le pire cas possible sur le terrain — une donnée perdue qui a l'air enregistrée.

Étape 3, le mot important est « enchaîne » : sur un déchargement de camion, l'agent scanne toutes les deux secondes. Un spinner réseau à chaque geste rendrait l'app inutilisable.

Termine en annonçant la suite : « une app qui promet doit savoir se dédire ».

12 Réconciliation

Vider la file :
quatre réponses possibles

Le moteur de synchro rejoue les lignes dans l'ordre de création, et une seule question se pose à chaque réponse du serveur : recommencer, abandonner, ou demander à l'humain ?

RéponseDécisionCe qui se passe
2xxsuccèsla ligne est supprimée, l'équipement est réécrit depuis la réponse du serveur (version incluse)
409conflitquelqu'un est passé avant : la ligne est marquée conflict et remonte dans le centre de synchro
422 invalid_transitionconflitl'état réel n'est plus celui qu'on croyait : même traitement, c'est un désaccord, pas une panne
5xx / réseauréessaice n'est pas un désaccord, c'est une indisponibilité : on retente plus tard
L'ordre FIFO n'est pas cosmétique : une transition dépend de la précédente. « Chargement » doit être rejoué avant « déploiement », sinon le serveur refuse une transition pourtant légitime.

Conduite

La distinction à faire comprendre est celle entre désaccord et panne. Une panne se retente : le serveur redeviendra disponible. Un désaccord ne se retente pas — le rejouer cent fois donnerait cent fois 409. Il faut un arbitrage humain.

C'est pour ça que decideReconcile est une fonction pure de trois lignes, isolée dans domain/ : c'est la décision la plus importante du moteur, elle doit être lisible et testable seule.

Le 422 item.invalid_transition mérite un mot : techniquement c'est une erreur de validation, mais fonctionnellement c'est un conflit — l'équipement n'est plus dans l'état que l'agent croyait. Je le route donc vers l'arbitrage, pas vers le réessai.

13 Réconciliation

Savoir insister,
savoir renoncer

Insister — le repli exponentiel

nextDelayMs = min(1000 × 2^tentatives, 60 000)

1 s → 2 s → 4 s → 8 s → 16 s … plafonné à 1 min

Sans plafond, la 10ᵉ tentative attendrait 17 minutes. Sans progression, 200 agents qui retrouvent le réseau en même temps au démontage feraient tomber l'API — c'est exactement le pic de charge annoncé en MP3.

Renoncer — le rollback visuel

tentative 5Échec définitif — l'effet local est annulé, la ligne est suppriméerollback

C'est la contrepartie de l'optimistic UI, et l'exigence explicite du sujet. L'app a affirmé « déployé ». Si le serveur ne l'a jamais accepté, elle doit se dédire — sinon l'agent repart avec une information fausse, et c'est pire que pas d'information du tout.

Le rollback est optionnel par action : un pointage n'a rien modifié localement, il n'a rien à annuler.

Le résultat d'une synchro n'est donc pas « ça a marché / ça n'a pas marché », mais quatre compteurs : synchronisées, en conflit, en échec temporaire, annulées. Le centre de synchronisation les affiche tels quels — l'agent voit exactement où il en est.

Conduite

Le repli exponentiel se justifie par le MP3 : j'y ai parlé des pics de charge au montage et au démontage. Le voici traité côté client — si chaque téléphone réessaie toutes les secondes, c'est l'API qui trinque. Le client participe à la tenue de charge du serveur.

Le rollback est l'exigence la plus subtile du sujet. Formule-la simplement : « l'app a le droit de mentir un instant, à condition de savoir se corriger. »

Si on demande pourquoi 5 tentatives : c'est un réglage, pas une loi — SYNC_MAX_ATTEMPTS dans config/env.ts. Cinq tentatives couvrent environ 30 secondes de réseau instable ; au-delà, ce n'est plus un passage sous un pont, c'est un vrai problème qui mérite d'être signalé à l'agent.

14 Un bug réel

Deux écrans,
deux synchros,
un doublon

Le symptôme

Au retour du réseau, certaines actions partaient deux fois. L'API n'étant pas idempotente sur les scans, l'historique d'un équipement se retrouvait avec deux mouvements identiques.

La cause

useSync est monté dans plusieurs écrans, et React Navigation garde les onglets vivants. Au retour du réseau, chaque instance du hook déclenchait sa propre synchro. Deux flushes lisaient la même file au même moment.

tentative 1Un garde-fou dans le hook — inopérant : chaque instance a son propre étatéchec
solutionUn verrou au niveau du module — une seule fois pour toute l'app ; un appel concurrent renvoie null au lieu de dupliquerrésolu
Le verrou est relâché dans un finally : sans ça, une erreur réseau bloquerait définitivement toute synchro ultérieure. Le remède aurait été pire que le mal.

Conduite

Slide volontairement « honnête ». Un jury retient mieux un bug raconté qu'une fonctionnalité listée, et ça prouve que l'app a réellement tourné sur un téléphone.

Le point technique à faire passer : un état porté par un hook est local à son instance. Quand l'unicité doit valoir pour toute l'application, elle doit vivre au niveau du module. C'est une leçon d'architecture React, pas un détail.

Le finally est le vrai raffinement : un verrou qu'on oublie de relâcher est un verrou pire que pas de verrou. C'est exactement l'argument que j'ai donné en MP3 contre le verrouillage pessimiste.

15 Scan industriel

D'un QR code
au bip, sans réseau

①Détection, sur le thread natifVision Camera repère le code sans faire traverser chaque image au pont JS.
②Anti-doublonLe même code vu il y a moins de 1,5 s est ignoré — sinon la caméra l'enfilerait des dizaines de fois par seconde.
③Résolution localeSELECT * FROM items WHERE qrCode = ? — index, base synchrone, environ 1 ms. Aucun appel réseau.
④Feedback immédiatVibration + bip. Vert si l'équipement est reconnu et le geste autorisé, rouge sinon. L'agent ne regarde pas l'écran.
⑤Position, puis empilementLe GPS est interrogé pour ce scan précis, puis la ligne part dans la file sortante.
Aucune de ces cinq étapes ne touche au réseau. C'est ce qui permet de vider un camion entier en zone blanche — et c'est aussi pour ça que le scan reste rapide même avec du réseau : il ne l'attend jamais.

Conduite

La phrase à retenir, dis-la telle quelle : « le scan ne dépend pas du réseau, même quand il y en a ». Ce n'est pas un mode dégradé qui s'active en cas de panne, c'est le seul chemin de code.

L'ordre des étapes 4 et 5 est délibéré : le retour haptique part avant l'écriture en base. L'agent perçoit la réponse à l'instant où il vise, pas après la persistance.

Si on demande « et si le QR n'est pas dans le cache ? » — bip rouge, l'équipement est listé comme non identifié. Ça arrive pour les 15 QR du jeu de démo qui appartiennent à un autre secteur : c'est le comportement voulu, l'agent ne doit pas manipuler du matériel qui n'est pas le sien.

Si on demande la latence : je ne l'ai pas instrumentée au millimètre, je l'ai validée à l'usage sur iPhone. Le facteur limitant est la caméra, pas le code.

16 Un bug réel

Le QR qui se
rescannait tout seul

Le symptôme

En laissant la caméra pointée sur une étiquette, le même équipement était réenfilé dans la file toutes les 1,5 seconde. Un agent qui pose son téléphone sur un carton génère cinquante lignes en deux minutes.

La correction, en un mot

La fenêtre court désormais depuis la dernière vue du code, pas depuis le dernier scan accepté. Chaque image repousse l'échéance : le code doit quitter le champ pendant 1,5 s pour être accepté à nouveau.

isDuplicate(code, now) {
  const prev = lastSeen.get(code);
  lastSeen.set(code, now);          // ⚠ repoussé à chaque vue, doublon ou non
  return prev !== undefined && now - prev < windowMs;
}
Une ligne déplacée. C'est le genre de détail qui ne se voit ni dans une revue de code, ni dans un test unitaire écrit d'après la spec — il se voit en tenant le téléphone.

Conduite

Deuxième bug raconté, et il complète le premier : celui-là ne pouvait être trouvé qu'en usage réel. Assume-le, c'est ton argument « j'ai vraiment testé sur device ».

Explique la nuance : la première version demandait « ce code a-t-il été accepté il y a moins de 1,5 s ? ». La bonne question est « ce code a-t-il disparu du champ depuis 1,5 s ? ». Ce n'est pas la même chose dès que la caméra produit soixante images par seconde.

La fonction est isolée dans services/scan/ScanService.ts et testée seule — la correction est couverte par un test qui simule un flux d'images.

Le risque, et comment je le tiens

Deux copies d'une même règle peuvent diverger. L'API reste l'autorité : la copie client est une optimisation d'expérience, tout est revérifié à la synchro. Et une sonde d'intégration compare les deux matrices contre l'API réelle — si elles divergent, le test casse.

Conduite

Rappelle la machine à états du MP3 — six états, transitions strictes, tout ce qui n'est pas autorisé est interdit. Ici, elle est rejouée côté client.

Anticipe la critique, elle viendra : « vous dupliquez une règle métier, c'est une faute ». Réponds avant qu'on te la pose, avec la carte de droite. La duplication est assumée, documentée et testée — la différence entre une dette et une décision, c'est qu'une décision se justifie.

Le vrai argument : sans validation locale, un agent en zone blanche scannerait cinquante équipements sans le moindre retour d'erreur, et découvrirait ses cinquante refus deux heures plus tard. C'est inacceptable sur le terrain.

19 Démonstration

Deux filtres,
isolés l'un de l'autre

Un geste peut être refusé pour deux raisons très différentes : l'état de l'équipement, ou le rôle de qui le tient. J'ai construit deux mises en situation qui les séparent proprement.

① Responsable logistique

Un seul QR : le groupe électrogène, en transit.

  • Pointage — accepté, ne change rien
  • Déploiement — accepté, in_transit → deployed
  • Transit — refusé : in_transit → in_transit interdit

Une fois déployé, le même QR inverse ses réponses — et un scan en Transit le ramène à son point de départ. La démonstration boucle, elle se rejoue sans reseed.

Ce qu'elle prouve : aucun refus ne vient du rôle. Ce compte a six gestes sur sept — tout sauf créer des comptes. Tous les refus viennent du statut.

② Transporteur, en mode avion

Deux QR : un chapiteau en transit, un bloc sanitaire déployé.

  • Pointage et Transit — acceptés, hors réseau
  • Déploiement — mode verrouillé, cadenas visible avant même de scanner
  • Maintenance — bouton absent de la fiche, avec sa raison

Or in_transit → deployed et deployed → in_maintenance sont deux transitions parfaitement légales : un agent de terrain réussirait sur ces mêmes QR.

Ce qu'elle prouve : ici, seul le rôle bloque — et il bloque sans réseau, instantanément.

Conduite

C'est la slide qui annonce ta démonstration. Insiste sur la construction des deux cas : j'ai choisi les équipements pour que les deux règles soient séparables. Sur un équipement pris au hasard, un refus est ambigu — le jury ne saurait pas si c'est le statut ou le rôle qui a parlé.

Le cas ② est le plus fort : les transitions refusées sont légales pour un autre rôle. C'est la preuve que le RBAC fonctionne, et qu'il fonctionne hors réseau, sur une matrice embarquée.

Rappelle la règle d'or de la démo hors ligne : connexion et téléchargement du secteur avant de couper. Le login est le seul geste qui exige le réseau.

Si on demande pourquoi le transporteur garde l'anomalie et la perte : il est le mieux placé pour constater une casse survenue pendant l'acheminement. Lui fermer ce geste ferait perdre l'information.

20 Sécurité

Ce qu'un téléphone
perdu ne doit pas livrer

  • Jetons dans le trousseau iOS — react-native-keychain, jamais en stockage clair. Un téléphone égaré sur un festival ne donne pas accès à la plateforme.
  • Rafraîchissement transparent — un 401 déclenche POST /auth/refresh et rejoue la requête. L'agent n'est jamais déconnecté au milieu d'un geste ; si le rafraîchissement échoue, retour à l'écran de connexion.
  • Mot de passe temporaire imposé — un compte créé par l'admin arrive avec mustChangePassword. L'app le détecte au démarrage et bloque l'accès aux écrans métier tant que le mot de passe n'a pas été remplacé — exactement comme le middleware côté API.
  • HTTPS strict, sauf en local — l'exception NSAllowsLocalNetworking de l'Info.plist ne couvre que le réseau local pour les démos. Une IP publique en clair serait refusée par App Transport Security.
  • Validation avant l'envoi — les schémas Zod du client reprennent ceux de l'API : retour immédiat sur un formulaire, y compris hors ligne. L'API revalide de toute façon.

Conduite

Reprends la logique du MP3 : la sécurité n'est pas une couche ajoutée à la fin. Mais côté mobile, la menace est différente — ce n'est plus l'attaquant réseau, c'est le terminal perdu ou volé. Le contexte est un festival avec des milliers de personnes.

Le mot de passe temporaire est le bon exemple de cohérence bout-en-bout : la règle est portée par le jeton côté API, l'app la lit et adapte sa navigation. Aucun des deux ne fait confiance à l'autre.

Si on demande pourquoi une exception HTTP dans l'Info.plist : uniquement pour pointer sur l'API locale pendant le développement et les démonstrations. Elle est limitée au réseau local par iOS lui-même, elle ne peut pas servir à joindre un serveur public en clair.

21 Matériel & temps réel

Écouter, localiser,
sans vider la batterie

Alertes en direct

L'app s'abonne au flux SSE que l'API expose déjà — celui que j'ai présenté en MP3, alimenté par les Change Streams MongoDB. Une anomalie déclarée par un agent apparaît chez les autres sans qu'aucun ne rafraîchisse quoi que ce soit.

GET/notifications/stream — jeton passé en paramètre, l'API l'accepte pour ce fluxSSE

Le flux est fermé dès que l'app passe en arrière-plan. Une connexion ouverte en permanence sur une journée de montage, c'est de la batterie pour rien.

Position

  • À la demande, jamais en continu — le GPS est interrogé au moment du scan et du signalement, puis relâché. Aucun suivi en arrière-plan.
  • Pas de position, pas de scan — un scan sans coordonnées n'a aucune valeur logistique : l'action est refusée avec un bip rouge plutôt qu'enregistrée à moitié.
  • Carte des zones — les polygones GeoJSON de l'événement et la position des équipements, lus depuis le cache local.
C'est la réponse à l'exigence « batterie et mémoire » du sujet : aucun polling réseau nulle part. L'app réagit à des événements — retour du réseau, alerte poussée, geste de l'agent — au lieu d'interroger en boucle.

Conduite

Rappelle la mesure du MP3 : environ 7 ms entre l'action terrain et la réception SSE. Ici, tu montres l'autre bout du fil — le consommateur.

Le refus de scan sans GPS est un choix discutable, sois prête à le défendre : un scan sert à savoir où se trouve un équipement. Sans coordonnées, la donnée est incomplète et faussement rassurante. Je préfère un refus explicite à une donnée trompeuse.

22 Pilotage

Les KPI, en lecture
seule et en ligne

Ce que l'app affiche

  • État des stocks par statut et par catégorie
  • Empreinte carbone consolidée de l'événement — fabrication amortie + transport
  • Facteurs d'émission issus de l'API Open Data de l'ADEME, en direct

Tout est calculé par le pipeline d'agrégation $facet côté MongoDB, présenté en MP3. L'app ne recalcule rien : elle affiche.

Une limite assumée

Les KPI ne fonctionnent pas hors ligne. C'est délibéré : un indicateur consolidé calculé sur un cache partiel serait faux, et un chiffre faux sur un tableau de bord est pire qu'un chiffre absent — il sera utilisé pour décider.

Hors réseau, l'écran affiche ce qu'il en est plutôt qu'une valeur périmée sans le dire.

C'est la frontière du choix offline-first : on met hors ligne ce qui doit être capturé (les gestes de l'agent), pas ce qui doit être exact (les indicateurs de pilotage).

Conduite

Ne survends pas cette partie : elle est en lecture seule et c'est normal, le pilotage n'est pas le métier de l'agent de terrain. Ce qui compte, c'est la justification de la limite.

La phrase à garder : « un chiffre faux est pire qu'un chiffre absent, parce qu'on décide avec ». C'est un argument de conception, pas un aveu de manque.

Si on demande de rappeler la méthode ADEME : deux termes, la fabrication amortie sur la durée de vie au prorata des jours d'événement, et le transport en tonnes × km × facteur d'émission. Les facteurs viennent en direct de l'API ADEME avec un repli codé en dur si elle est indisponible. Tout ça est côté API, je l'ai détaillé en MP3.

23 Pilotage

Qu'est-ce qui fait
bouger un indicateur ?

Question posée en répétition, et elle mérite une réponse précise : si les agents scannent toute la journée, pourquoi l'empreinte carbone ne bouge-t-elle pas ?

Ce qu'un scan change

La répartition par statut. Les six tuiles du tableau de bord se recalculent — et hors réseau, car elles sont dérivées du cache SQLite, pas d'un appel serveur. C'est le seul indicateur qui vit en zone blanche.

Ce qu'un scan ne change pas

L'empreinte carbone. Le pipeline d'agrégation fait $match: { eventId } et rien d'autre : il ne filtre jamais sur le statut. Déplacer un équipement d'un état à l'autre ne change ni sa fabrication, ni son transport.

Ce qui la fait bouger : l'allocation

avant80,94 kg — 51 équipements dans le périmètreétat initial
POST/events/:id/allocate — 3 équipements, transaction ACID tout-ou-rienle MP3 rejoué
après88,34 kg — dont +5,84 kg pour le seul groupe électrogène : 8 000 kg de CO₂ amortis sur 15 ans, au prorata de 4 jours+7,40 kg
Le carbone répond aux décisions de planification — allouer, organiser une tournée — pas aux gestes du terrain. Le pont existe pourtant côté API : actualDistanceKm. Le scan capture déjà une position GPS horodatée ; en déduire la distance réellement parcourue ferait enfin vivre le carbone au rythme du terrain. Je ne l'ai pas fait : deux points GPS donnent une distance à vol d'oiseau, pas des kilomètres routiers — et un chiffre faux est pire qu'un chiffre absent.

Conduite

Slide de démonstration en direct : lance ./demo-kpi.sh alloc, puis rafraîchis l'onglet KPI sur le téléphone. Le chiffre bouge sous les yeux du jury. Pense à lancer reset après — deux des équipements alloués font partie des QR hors secteur.

Double bénéfice à annoncer : l'endpoint d'allocation, c'est la transaction ACID du MP3. Un seul geste prouve que l'indicateur est vivant et que la transaction fonctionne.

Le dernier paragraphe est ta meilleure réponse à « et ensuite ? ». Tu montres que tu as identifié le chaînon manquant et pourquoi le combler naïvement dégraderait la mesure. C'est plus solide que de prétendre que tout est branché.

Si on objecte « alors les KPI ne servent à rien dans l'app » : dans l'app mobile, oui, l'onglet KPI est le seul écran qui ne réagit à aucun geste de son utilisateur — parce que les gestes qui le font bouger sont ceux du responsable, que j'ai exclus du périmètre. C'est une conséquence du périmètre, pas de l'indicateur.

Pourquoi c'est rapide

Les règles métier vivent dans domain/, sans dépendance à React Native ni à un appareil : machine à états, décision de réconciliation, matrice de permissions, repli exponentiel, filtrage, résolution du thème. Les dépôts SQLite sont testés sur une base en mémoire. Aucun simulateur n'est nécessaire.

27 Honnêteté

Ce que je n'ai pas fait,
et pourquoi

  • Pas de tests de rendu — react-native-testing-library n'est pas installée. Les composants sont testés par leurs fonctions pures (filtrage, visibilité selon le rôle, libellés) ; le rendu visuel et les contrastes sont validés à la main sur iPhone. Limite assumée, pas oubliée.
  • Android non validé — le code est cross-platform et ne contient aucune API spécifique à iOS, mais je ne l'ai testé que sur iPhone. Je ne prétendrai pas qu'il tourne sur Android : je ne l'ai pas vérifié.
  • Écrans admin absents — hors périmètre, choisi. L'app cible l'agent de terrain ; seule la création de compte est disponible, parce que l'API l'expose déjà.
  • Résolution de conflit manuelle — l'app détecte le conflit, l'affiche avec l'état local et l'état serveur, et laisse l'agent trancher. Une fusion automatique déciderait à sa place sur une donnée physique qu'il est le seul à pouvoir constater.
Ces quatre points sont des décisions, pas des oublis. C'est la différence que je veux montrer : un périmètre tenu et documenté vaut mieux qu'un périmètre affiché et creux.

Conduite

Slide courageuse, garde-la. Un jury pose toujours la question des limites — mieux vaut l'avoir posée soi-même, avec la justification prête.

La quatrième ligne est la plus intéressante : la résolution manuelle des conflits n'est pas de la paresse. Sur un conflit de statut d'équipement, seul l'agent qui a l'objet sous les yeux sait qui a raison. Une fusion automatique produirait une donnée que personne n'a constatée.

Ne t'excuse pas en disant ça. Ce sont des arbitrages, énonce-les comme tels.

Lève les yeux.

Sigles : FIFO = premier entré, premier sorti. SSE = Server-Sent Events, flux poussé par le serveur. JSI = l'interface qui permet à op-sqlite d'être synchrone. ATS = App Transport Security, la politique HTTPS d'iOS.

« Pourquoi pas une base de données synchronisée toute faite ? » — Parce que le sujet impose la réconciliation avec une API REST existante et son verrouillage optimiste. Une solution clé en main aurait imposé son propre modèle de synchronisation, et je n'aurais rien démontré du mécanisme.

« Comment démontrer le mode hors ligne ? » — Mode avion, scanner trois équipements, montrer le compteur de la file qui monte, réactiver le réseau, montrer la file qui se vide et les statuts qui se mettent à jour.
